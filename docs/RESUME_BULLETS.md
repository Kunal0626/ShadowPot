# Resume bullets

Candidate bullets for ShadowPot, split by whether the evidence for them
exists **today**.

Every number in the "usable now" section traces to a command in this
repository. Every bullet in the "needs a deployment" section is marked
`needs:` and must not be used until that evidence exists.

---

## What makes a bullet defensible

Three tests, applied to each bullet below.

1. **Can you name the command that produced the number?** If not, the number
   is a guess and an interviewer who asks "how do you know?" ends the
   conversation.
2. **Would the number survive being asked "measured on what?"** A throughput
   figure without its hardware and its input size is not a measurement.
3. **Does the verb match what you actually did?** "Built a pipeline that
   processed N events" is defensible. "Detected and blocked attacks" is not,
   because nothing here blocks anything and a honeypot has nothing to protect.

## Usable now

These describe engineering that exists, with numbers measured on this machine.
Both say "synthetic" or "generated", because that is what was measured, and
leaving it out would be the kind of omission that collapses under one
follow-up question.

### Bullet 1 — the pipeline

> **Built an SSH-honeypot analytics pipeline** (Python 3, SQLite/MySQL) that
> parses Cowrie's JSON event log into a 12-table normalized schema and answers
> 18 analytical questions in SQL; the loader is idempotent and crash-resumable
> and **ingested 160,708 generated log lines in under 9 s**, covered by
> **364 tests**.

**Evidence for each number**

| Claim | Where it comes from |
|---|---|
| 12 tables, 18 queries | `docs/MEASUREMENTS.md`, regenerated by `python3 tools/measure.py` |
| 160,708 lines in under 9 s | same, "30 days" row. Synthetic logs, macOS arm64, Python 3.14.6, SQLite 3.50.4 |
| 364 tests | `make test` |
| idempotent, crash-resumable | `tests/test_ingest.py`, classes `TestIdempotence` and `TestResumability` |

**Why "under 9 s" and not a rate.** Five timed runs of that load ranged from
6.00 s to 8.84 s depending on what else the machine was doing. Quoting
"26,780 lines/s" would be quoting the luckiest run as though it were a
property of the code, and it collapses the moment an interviewer -- or you --
re-runs it. A bound derived from the slowest run does not. This is the single
most common way a resume number becomes indefensible: not fabrication, just
false precision.

**Shorter variant, if space is tight:**

> Built an SSH-honeypot log analytics pipeline in Python and SQL: a 12-table
> normalized schema, an idempotent crash-resumable loader that handles 160k
> generated log lines in under 9 s, and 18 analytical queries. 364 tests.

### Bullet 2 — the database work

> **Designed the schema in 3NF from Cowrie's event format**, deriving the
> functional dependencies and documenting the 1NF→3NF decomposition; found that
> a nullable column silently defeats a `UNIQUE` constraint (SQL treats NULLs
> as distinct) and replaced it with a `CHECK`-enforced exclusive arc;
> **measured 7 candidate indexes with `EXPLAIN QUERY PLAN` and shipped the 4
> that changed a query plan**, rejecting the rest.

**Evidence for each number**

| Claim | Where it comes from |
|---|---|
| 3NF derivation, FDs, 1NF→3NF | `docs/NORMALIZATION.md` |
| NULLs defeat UNIQUE | measured; `tests/test_schema.py::test_counterfactual_nullable_password_does_not_deduplicate` |
| 7 measured, 4 kept | `docs/INDEXES.md`, regenerated by `make bench` |

This is the stronger of the two bullets for a DBMS-heavy role, and the
NULL/`UNIQUE` detail is the part most likely to start a real conversation,
because it is a thing many people with "SQL" on their resume do not know.

## Needs a deployment

**Do not use these yet.** Each carries what is missing. Once
`docs/DEPLOY.md` has been executed and `reports/real-report.md` exists, fill
the blanks from the recording template in that document's §10.

### Bullet 3 — the actual finding

> Deployed an SSH honeypot on an isolated VPS for ___ days, capturing ___
> sessions and ___ login attempts from ___ unique source addresses; SQL
> analysis showed ___ credential pairs arriving from 5+ distinct addresses,
> indicating shared botnet wordlists.

`needs:` a real 7-day deployment. Every blank comes from
`reports/real-report.md`. The sample data cannot fill these in — it is
generated, every address is from a reserved documentation range, and using
those numbers would be fabrication.

### Bullet 4 — the operational angle

> Hardened and operated the deployment: relocated the host's `sshd`, restricted
> egress so the honeypot could not be used to attack third parties, and
> automated daily log retrieval and reporting via cron, processing ___ days of
> real capture with ___ malformed lines and zero duplicated rows across ___
> incremental loads.

`needs:` the deployment, plus the `ingest_runs` table from the real database:

```bash
sqlite3 data/real.db 'SELECT COUNT(*), SUM(lines_read), SUM(lines_malformed) FROM ingest_runs;'
```

### Bullet 5 — classification, if the heuristic survives real data

> Classified ___% of shell sessions as scripted rather than hand-driven using
> command-timing and sequence-reuse heuristics in SQL window functions.

`needs:` real data **and** a judgement about whether the 250 ms threshold
holds up. On generated data the populations separate by construction, so the
current split (99 scripted / 53 human-like) demonstrates the SQL and validates
nothing. If the real distribution is not bimodal, this bullet should be
dropped rather than reworded.

## Bullets not to write

Anti-examples. Each is the kind of sentence that reads well and does not
survive a follow-up question.

| Don't write | Why it fails |
|---|---|
| "Detected and **blocked** 10,000+ attacks" | Nothing here blocks anything. A honeypot has no production service to protect. The first follow-up is "blocked how?" |
| "Secured infrastructure against SSH brute-force attacks" | The opposite of what happened: a machine was deliberately exposed. |
| "Identified attackers from 40+ countries" | Not measured. There is no GeoIP database in this project and no live lookups, by design. |
| "Captured and **analysed** malware samples" | Hashes were recorded. The samples were never run or reverse-engineered, and saying "analysed" invites a question about the analysis. |
| "Processed millions of events" | Not measured. The largest run in evidence is 160,708 lines. |
| "Built a real-time threat detection system" | It is a batch pipeline driven by a daily cron. |
| "Reduced false positives by X%" | There is no baseline and no detector. A honeypot has no false positives to reduce, which is a genuinely interesting point to make *instead* of this. |

## One line for a portfolio or LinkedIn

Supportable today:

> ShadowPot — an SSH honeypot analytics pipeline: Cowrie's JSON event log into
> a 3NF SQL schema, with an idempotent incremental loader, 18 analytical
> queries, measured index tuning, and 364 tests. Deployment runbook included;
> real-world capture pending.

(When the deployment is done, replace "real-world capture pending" with the
days and session count. Until then, leave it in: it is the clause that makes
the rest of the sentence trustworthy.)

That last clause is doing real work. It is the difference between a project
that is honest about its state and one that an interviewer catches out.
